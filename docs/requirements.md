# 要件定義: GNSS / LiDAR 自己位置推定

- 関連文書: [設計書](./design.md)（v0.9） / [ソフトウェア構成](./architecture.md) / [アルゴリズム説明書](./algorithm.md)
- 変更: 設計書 v0.9 に合わせて、運用上の前提（3 章）と FR-8（デッドレコニングの監視）を追加した

## 1. 目的

RTK-GNSS が利用できる区間と利用できない区間をまたいで走行する移動体に対し、経路追従に使用できる連続した自己位置を提供する。

## 2. 機能要件

| ID | 項目 | 内容 |
|---|---|---|
| FR-1 | 推定方式 | GNSS が RTK-FIX する区間では GNSS を、それ以外の区間では事前作成した点群地図を用いた LiDAR マッチングにより自己位置を推定する |
| FR-2 | 使用センサ | GNSS、LiDAR、オドメトリ（ODOM）、IMU |
| FR-3 | 出力座標系・自由度 | UTM 座標系。出力する自由度は当面 x, y, yaw の 3 自由度とする |
| FR-4 | 出力の連続性 | 推定ソースや点群地図の切り替え時にも自己位置が不連続に変化（ジャンプ）しないこと。自己位置は経路追従に使用される |
| FR-5 | 経路 | 経路は UTM 座標系で 1 本として与えられる |
| FR-6 | 複数地図 | 点群地図は複数存在しうる（下記「3. 想定する区間構成」） |
| FR-7 | 地図の動的ロード | 点群地図を統合・タイル分割し、自己位置周辺のみを動的に読み込む（部分展開） |
| FR-8 | デッドレコニングの監視 | 位置の観測（RTK-FIX の GNSS、または点群地図との LiDAR 照合）が得られないまま一定の距離（パラメータ）を走行したら、diagnostics でエラーメッセージを通知する |

## 3. 想定する区間構成

- 例1: `点群地図1 ↔ GNSS ↔ 点群地図2`
- 例2: `GNSS ↔ 点群地図1 ↔ 点群地図2`

点群地図どうしが直接接続する区間には、地図間のオーバーラップ領域が存在する。

**運用上の前提**（v0.9 で追加）: 点群地図と GNSS 区間の間には、必要十分な距離が設定される。本システムでは、これを次の意味に解釈して設計する。

- 例1 のように GNSS 区間をはさむ地図どうし（別の地図グループ。設計書 5.1 節）は重ならない。間の GNSS 区間は、RTK-FIX を得て安定し、GNSS で位置を確定できるだけの長さがある。
- 地図の範囲と RTK-FIX が得られる範囲の境目で、どちらの観測も得られない区間（デッドレコニングでつなぐ区間）は短い。

この前提が崩れた（想定より長くデッドレコニングが続いた）ことは、FR-8 で検知して通知する。

## 4. 点群地図の前提

- 各点群地図は独自の地図座標系を持つ。
- 各点群地図について、ある地点の緯度経度および向き（方位）が既知である。これにより「地図座標系 → UTM」の剛体変換が定まる。
- 例2 のように GNSS 区間に接しない地図を、隣接地図経由で UTM に変換すると、アンカー誤差（特に方位誤差）が連鎖・蓄積して歪みが大きくなる懸念がある。
  - このため、隣接する地図は統合してタイル分割し、動的ロードする方針とする（FR-7）。これにより、すべての地図領域を「GNSS ↔ 点群地図」の関係のみで扱えるようにする。
- （v0.9 で追加）各点群地図の z 軸は鉛直（重力の方向）にそろっているものとする。アンカーによる変換は、鉛直軸まわりの回転と高さのずれだけを扱うため（設計書 5.1 節。確認事項は設計書 11 章）。
- （v0.9 で追加）同じ水平位置に高さの違う地図が重なる構成（立体駐車場の階など）は対象外とする。

## 5. 非機能要件（ソフトウェア構成）

| ID | 項目 | 内容 |
|---|---|---|
| NFR-1 | ミドルウェア | ROS 2 **Jazzy** を使用する |
| NFR-2 | 層分離 | ROS のインターフェース層とロジック層を分離する。ロジック層は ROS に依存しない |
| NFR-3 | 移植性 | インターフェース層の差し替えのみで ROS 1 に移行できること。**ROS 1 対応の実装は後回し**とし、当面は移行できる構造を保つことだけを求める |
| NFR-4 | 開発環境 | 開発・ビルド・テスト・データ変換の環境は **Docker** で構築する |
| NFR-5 | 出力 TF | `map` → `base_link` を直接出す（odom フレームは使わない）。`map` は UTM 座標系 |

## 6. 設計時の検討事項（設計書で決定済み）

以下は要件定義の時点で未決だった論点である。決定の内容は設計書を参照。

- 1 → **(B) 単一の推定器**（Invariant EKF）で全センサを融合する（設計書 1 章 D-1、D-2）。
- 2 → 直接つながる地図は 1 つの地図グループに統合し、タイル分割して先読みで動的にロードする。どのグループで照合するかは現在位置で決める（設計書 5 章）。GNSS 区間と地図区間の引き継ぎは、優先度・食い違いの判定・再アンカーで扱う（設計書 3.13 節）。

当初の論点:

1. **推定アーキテクチャ**:
   - (A) GNSS localizer と LiDAR localizer を個別に持ち、出力を切り替える
   - (B) 単一の推定器（EKF / ファクターグラフ等）で全センサを融合し、利用可能な観測のみを反映する

   FR-4（ジャンプ不可）が選定に大きく影響する。
2. **地図の切り替え・読み込み**:
   - 地図の統合単位とタイルサイズ
   - タイルのロード / アンロードのタイミング（先読み範囲など）
   - GNSS 区間と地図区間の引き継ぎ方法（オーバーラップ区間での整合確認など）
