# 要件定義: GNSS / LiDAR 自己位置推定

## 1. 目的

RTK-GNSS が利用できる区間と利用できない区間をまたいで走行する移動体に対し、経路追従に使用できる連続した自己位置を提供する。

## 2. 機能要件

| ID | 項目 | 内容 |
|---|---|---|
| FR-1 | 推定方式 | GNSS が RTK-FIX する区間では GNSS を、それ以外の区間では事前作成した点群地図を用いた LiDAR マッチングにより自己位置を推定する |
| FR-2 | 使用センサ | GNSS、LiDAR、オドメトリ（ODOM）、IMU |
| FR-3 | 出力座標系・自由度 | UTM 座標系。出力する自由度は当面 x, y, yaw の 3 自由度とする |
| FR-4 | 出力の連続性 | 推定ソースや点群地図の切り替え時にも自己位置が不連続に変化（ジャンプ）しないこと。自己位置は経路追従に使用される |
| FR-5 | 経路 | 経路は UTM 座標系で 1 本として与えられる |
| FR-6 | 複数地図 | 点群地図は複数存在しうる（下記「3. 想定する区間構成」） |
| FR-7 | 地図の動的ロード | 点群地図を統合・タイル分割し、自己位置周辺のみを動的に読み込む（部分展開） |

## 3. 想定する区間構成

- 例1: `点群地図1 ↔ GNSS ↔ 点群地図2`
- 例2: `GNSS ↔ 点群地図1 ↔ 点群地図2`

点群地図どうしが直接接続する区間には、地図間のオーバーラップ領域が存在する。

## 4. 点群地図の前提

- 各点群地図は独自の地図座標系を持つ。
- 各点群地図について、ある地点の緯度経度および向き（方位）が既知である。これにより「地図座標系 → UTM」の剛体変換が定まる。
- 例2 のように GNSS 区間に接しない地図を、隣接地図経由で UTM に変換すると、アンカー誤差（特に方位誤差）が連鎖・蓄積して歪みが大きくなる懸念がある。
  - このため、隣接する地図は統合してタイル分割し、動的ロードする方針とする（FR-7）。これにより、すべての地図領域を「GNSS ↔ 点群地図」の関係のみで扱えるようにする。

## 5. 非機能要件（ソフトウェア構成）

| ID | 項目 | 内容 |
|---|---|---|
| NFR-1 | ミドルウェア | ROS 2 を使用する |
| NFR-2 | 層分離 | ROS のインターフェース層とロジック層を分離する。ロジック層は ROS に依存しない |
| NFR-3 | 移植性 | インターフェース層の差し替えのみで ROS 1 に移行できること |

## 6. 設計時の検討事項（未決）

1. **推定アーキテクチャ**:
   - (A) GNSS localizer と LiDAR localizer を個別に持ち、出力を切り替える
   - (B) 単一の推定器（EKF / ファクターグラフ等）で全センサを融合し、利用可能な観測のみを反映する

   FR-4（ジャンプ不可）が選定に大きく影響する。
2. **地図の切り替え・読み込み**:
   - 地図の統合単位とタイルサイズ
   - タイルのロード / アンロードのタイミング（先読み範囲など）
   - GNSS 区間と地図区間の引き継ぎ方法（オーバーラップ区間での整合確認など）
