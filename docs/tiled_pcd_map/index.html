第 1 部　仕組み

1. なぜ部分ロードか

LiDAR で自己位置を推定するときは、スキャンを点群地図に重ねて（位置合わせして）位置を求める。位置合わせに要るのは、LiDAR が届く範囲（数十 m）の地図だけで、地図全体は要らない。

  • メモリ: 地図全体を読むと、地図が広くなるほどメモリが増える。西新宿の約 0.9 km × 1.1 km の地図でも、間引いた後で約 460 万点ある。
  • 検索の速さ: 位置合わせでは、スキャンの各点に最も近い地図の点を探す（KdTree）。探す相手が周りだけなら、木が小さくて済み、作り直しも速い。
  • 起動の速さ: 起動時に読むのは、各タイルの範囲と点数を書いた索引だけ。点群本体は必要になったときに読む。

2. 全体の流れ

地図のタイル化は事前に 1 回だけ行う（オフライン）。走行中は、自己位置が来るたびに必要なタイルを見直し、別のスレッドで読み込んで、照合に使う「領域」を差し替える。

3. 地図をタイルにする

tiled_pcd_map_tiler は、外部のツールで作った統合済みの点群（PCD）を読み、次の順に処理する。

  1. 間引く: 0.2 m のボクセルごとに点を平均して 1 点にする（既定）。
  2. 点ごとの共分散を計算する: 各点の近くの 20 点から、その点の周りの面の形（平面なら 1 方向だけ薄い楕円体）を求める。GICP の位置合わせに使う。
  3. タイルに分ける: 地図座標を 20 m で割って切り捨てた番号 (ix, iy) ごとに、点をタイルファイルに書く。

共分散はタイルに分ける前に、地図全体で計算する。分けた後で計算すると、タイルの境目の近くの点は、隣のタイルにある近傍点を使えないからである。

出力は、タイルごとの本体ファイル tiles/<ix>_<iy>.bin（点の xyz と共分散の上三角 6 要素、いずれも float32）と、全タイルの索引 tile_index.yaml（番号・ファイル名・点数・範囲）である。起動時に読むのは索引だけで、数百枚のタイルでも一瞬で済む。

4. どのタイルを読むか

自己位置を与えるたびに、各タイルについて「読むべきか」「持ち続けてよいか」を決める。距離は、タイルの中心ではなくタイルの四角形までの最短距離で測る。

  • 読み込む: 現在位置から 60 m（load_radius）以内のタイル。加えて、進行方向へ「速さ × 3 秒（lookahead_time）」進んだ先読み位置から 60 m 以内のタイル。
  • 持ち続ける: 読み込む範囲からは外れたが、現在位置から 90 m（unload_radius）以内のタイル。
  • 捨てる: 現在位置から 90 m より遠くなったタイル。

読み込む距離（60 m）と捨てる距離（90 m）の間に差があるので、境目の近くを行ったり来たりしても、同じタイルを読んでは捨てる、を繰り返さない。

「持ち続ける」タイルも、キャッシュにある限り照合の領域に入る（領域 = アクティブグループの読み込み済みタイル全部）。捨てる距離を読み込む距離より大きくしてあるのは、読み込み直しの手間を減らすためで、その分だけ領域は少し広くなる。

5. いつ見直すか

update() は自己位置が来るたびに呼んでよいが、実際に見直すのは次のどちらかのときだけである。

  • 前回見直した位置から 1 m（update_distance）以上動いた。
  • 前回から 1 秒（update_interval）以上たった（止まっていても、先読みやグループの判定を更新するため）。

見直した結果、要るタイルの組もアクティブグループ（8 章）も変わらなければ、何もしない。変わったときだけロードスレッドに通知して、すぐ戻る。タイルは 20 m 四方なので、1.5 m/s で走っていても、組が変わるのは数秒に 1 回程度である。

6. 読み込みと差し替え

ロードスレッドは通知を受けると、足りないタイルをファイルから読み、捨てるタイルをキャッシュから消し、読み込み済みのタイルで新しい「領域」を作る。できあがったら、今の領域と差し替える（ダブルバッファ）。

領域は shared_ptr で受け渡しする。照合の途中で差し替わっても、照合しているスレッドは古い領域を持ったまま最後まで計算でき、終わって手放した時点で古い領域が解放される。照合する側は、ロックを持ったまま待つ必要がない。

テストなどで順番を決めて動かしたいときは、async = false にすると、読み込みと領域の作成を update() の中で行う。waitIdle() で、読み込みが終わるのを待つこともできる。

7. 領域の中身を決める

「領域」に何を持たせるかは、使う側が決められる。MapTileManager には、読み込み済みのタイルから領域を作る関数（RegionBuilder）を渡す。この関数はロードスレッドで呼ばれるので、重い前処理（KdTree の構築など）をしても、使う側は止まらない。

8. 複数の地図

座標系の違う複数の点群地図（地図グループ）を扱える。各グループには、地図の 1 点の緯度経度と地図の向き（アンカー）を与え、タイルの四隅を UTM に直して判定する。すべてのグループのタイルが読み込みの対象になるが、領域を作るのは 1 つのグループ（アクティブグループ）だけで、別のグループの点を混ぜない。

  • アクティブグループは、現在位置（先読みは使わない）から 60 m 以内にあるグループのうち、タイルまでが最も近いもの。
  • 今のグループより 10 m（group_switch_margin）以上近いグループが現れたときだけ切り替える。境目で行ったり来たりしない。
  • 次のグループのタイルは、先読みで先にキャッシュに入る。切り替えた時点で、すぐに領域を作れる。

10. データ構造

型は 3 つのまとまりに分かれる。左は、ファイルから読む地図の情報で、起動時に読んだら変わらない。中央は MapTileManager の中の状態。右は、タイルの点群と、それから作る領域。

  • タイルの識別: ファイルには番号 ix・iy しか書かれていない（タイルファイルの中身には番号も無い）。番号はグループの中でしか一意でないので、読み込むときにグループ名を付けて TileId（グループ名・ix・iy）にする（TileIndex::load(path, group) が付け、BinaryTileLoader が読んだ TileData にも写す）。
  • 添字で扱う: MapTileManager の中では、全グループの全タイルを 1 列に並べた tiles_（vector<TileEntry>）を起動時に作り、以後はその添字（size_t）でタイルを指す。要るタイルの組・キャッシュ・領域に入れた組は、どれも添字の std::set / std::map なので、「前と同じ組か」は set の == で比べられる。
  • 点はコピーしない: タイルの点群 TileData は shared_ptr<const TileData> で持つ。キャッシュと既定の領域（TileSetRegion）は同じ TileData を指す。キャッシュから消しても、その TileData を指す領域が残っている間は解放されない。
  • 数値の型: 点は float の xyz（Vec3f）、共分散は上三角 6 要素の float（PackedCov = std::array<float, 6>）。距離の判定は UTM の double（Vec2）で行う。

11. タイル化とファイルの形式

コマンド tiled_pcd_map_tiler は、readPcd() で PCD を読み、tileMap() でタイルに分け、writeTiles() で書く。tileMap() の中身は次の順になる。

  1. voxelDownsample(): 点群の最小値 lo を原点にして、(p − lo) / voxel_size を切り捨てた整数 (ix, iy, iz) を 21 ビットずつ 64 ビットのキーに詰め、unordered_map で点の和と個数を数える。出力はボクセルごとの平均で、そのボクセルの点が最初に現れた順に並ぶ（同じ入力なら、同じ出力になる）。1 軸 221 個までなので、0.2 m なら約 419 km まで。超えると例外を投げる。
  2. 共分散（small_gicp 付きでビルドしたとき）: 間引いた点全体で KdTree を作り、estimate_covariances_omp() で各点の近くの num_neighbors 点から 4×4 の共分散を求め、上三角 6 要素を float で取り出す。--no-covariance のときや small_gicp なしでは、共分散を付けない。
  3. 分割: std::map<pair<int,int>, TileData> に、tileCoord(x)・tileCoord(y) をキーにして点を入れる。tileCoord(v) = floor(v / tile_size) なので、負の座標でも境目がずれない（x = −0.1 m は −1 番）。std::map なので、タイルは (ix, iy) の順に並ぶ。
  4. 索引: タイルごとに点の最小・最大（bounds_min / bounds_max）と点数を TileMeta にまとめ、TileIndex を作る。

12. 起動時の準備

起動時は、設定を読んで MapTileManager を作るところまで。ここでは点群本体を読まない。

  1. loadMapSetConfig("maps.yaml") → MapSetConfig（グループごとの ID・tile_index.yaml のパス・アンカーの設定）。
  2. loadMapGroups(cfg, utm) → vector<MapGroup>。グループごとに、アンカーを MapAnchor::fromConfig()（anchor: local なら恒等変換）で作り、索引を TileIndex::load() で読む。
  3. MapTileManager(cfg, groups, loader, builder, logger)。コンストラクタは全タイルについて TileEntry を作り、tiles_ に並べる。非同期モードなら、ここでロードスレッド（workerLoop()）を起動する。

TileEntry を作るときに、タイルの四隅を地図座標から UTM に直しておく。以後の距離の判定は、すべて UTM のこの四角形で行う。地図座標の点 p を UTM に直す MapAnchor::mapToUtm() は、水平は相似変換、高さは平行移動である。

qxy = autm + k · R(φ) · (pxy − amap)　　qz = autm,z + (pz − amap,z)

ここで amap と autm はアンカー点の地図座標と UTM 座標、φ は地図の x 軸の東からの角度（反時計回り）、k はアンカー点での UTM の縮尺係数（地図の実距離を UTM 上の距離に直す。1 に近く、中央子午線で 0.9996。設定の use_scale_factor: false なら 1）。回転があるので、UTM では四角形が傾く。

内側かどうかは、4 辺それぞれについて、辺のベクトルと「辺の始点 → p」の外積（z 成分）が 0 以上かで判定する。地図座標の四隅は反時計回りに並べてあり、回転と正の縮尺では向きが変わらないので、UTM でも反時計回りのまま。4 辺すべてで外積が 0 以上なら内側である。外接矩形までの距離は四角形までの距離以下なので、外接矩形の段階で遠いタイルを飛ばしても、読むべきタイルを落とすことはない。

13. update() の中身

void update(double t, const Vec2& position, double yaw, double speed, bool force = false)。位置と向きは UTM（x = 東、y = 北、yaw は東から反時計回り）、速さは m/s。呼び出し側のスレッドで、次の順に動く。

  1. 間引く: force でなく、前回の見直しから update_distance 未満しか動いておらず、update_interval 未満しかたっていなければ、すぐ戻る（last_position_・last_t_ は update_mtx_ で守る）。
  2. グループごとの距離 dg[g]: 全タイルを回って、グループごとに「現在位置からそのグループのタイルまでの最短距離」を求める。外接矩形までの距離が今の最小以上のタイルは飛ばし、最小が 0 になったグループは以後飛ばす。
  3. 最も近いグループ best: dg[g] ≤ load_radius のうち最小のもの（無ければ −1）。
  4. 先読み位置: ahead = p + lookahead_time · speed · (cos yaw, sin yaw)。
  5. 要るタイル needed: 全タイルについて、p か ahead から load_radius 以内なら添字を入れる。アクティブでないグループのタイルも入る（8 章の先読みはこれで起きる）。
  6. mtx_ を取って要求を書く: アクティブグループをヒステリシス付きで決め（16 章）、changed = (needed != requested_tiles_) || (active != requested_active_) を計算し、requested_tiles_・requested_active_・requested_position_ を上書きする。changed なら pending_ = true。
  7. 知らせる: changed のときだけ、非同期モードなら cv_.notify_one() でロードスレッドを起こし、同期モードなら processPending() をその場で呼ぶ。

どの手順も、全タイルを 1 回ずつ見る線形の走査で、空間索引（格子や木）は使っていない。西新宿の 936 タイルで、見直し 1 回が中央値 約 11 µs だった（18 章）。数万タイルの地図なら、ここを格子で引く形にする余地がある。

「捨てる」判定は update() ではなく、ロードスレッドの processPending() で行う。update() が決めるのは「要る組」と「アクティブグループ」だけで、それ以外のタイルをいつ消すかはキャッシュを持つ側が決める。

void MapTileManager::update(double t, const Vec2& p, double yaw, double speed, bool force) {
  std::lock_guard<std::mutex> ulk(update_mtx_);
  if (!force && have_last_ && (p - last_position_).norm() < cfg_.update_distance && t - last_t_ < cfg_.update_interval)
    return;
  have_last_ = true;
  last_position_ = p;
  last_t_ = t;

  // グループごとの、現在位置からタイルまでの距離
  std::vector<double> dg(groups_.size(), kInf);
  for (const TileEntry& e : tiles_) {
    double& d = dg[e.group_index];
    if (d == 0.0 || boxDistance(e.bb_min, e.bb_max, p) >= d) continue;
    d = std::min(d, distanceToTile(e, p));
  }
  int best = -1;
  for (std::size_t g = 0; g < groups_.size(); ++g)
    if (dg[g] <= cfg_.load_radius && (best < 0 || dg[g] < dg[static_cast<std::size_t>(best)])) best = static_cast<int>(g);

  // 必要なタイル（現在位置と、先読みした位置のまわり）
  const Vec2 ahead = p + cfg_.lookahead_time * speed * Vec2(std::cos(yaw), std::sin(yaw));
  const double R = cfg_.load_radius;
  std::set<std::size_t> needed;
  for (std::size_t i = 0; i < tiles_.size(); ++i) {
    const TileEntry& e = tiles_[i];
    const bool near_p = boxDistance(e.bb_min, e.bb_max, p) <= R && distanceToTile(e, p) <= R;
    const bool near_a = !near_p && boxDistance(e.bb_min, e.bb_max, ahead) <= R && distanceToTile(e, ahead) <= R;
    if (near_p || near_a) needed.insert(i);
  }

  bool changed = false;
  {
    std::lock_guard<std::mutex> lk(mtx_);
    int active = active_;
    if (active >= 0 && dg[static_cast<std::size_t>(active)] <= cfg_.load_radius) {
      // ヒステリシス: ほかのグループが group_switch_margin 以上近くなったときだけ切り替える
      if (best >= 0 && best != active &&
          dg[static_cast<std::size_t>(best)] < dg[static_cast<std::size_t>(active)] - cfg_.group_switch_margin)
        active = best;
    } else {
      active = best;
    }
    if (active != active_) {
      const std::string from = active_ >= 0 ? groups_[static_cast<std::size_t>(active_)].id : "(none)";
      const std::string to = active >= 0 ? groups_[static_cast<std::size_t>(active)].id : "(none)";
      logger_->info("active map group: " + from + " -> " + to);
    }
    active_ = active;
    stats_.active_group = active >= 0 ? groups_[static_cast<std::size_t>(active)].id : "";
    changed = needed != requested_tiles_ || active != requested_active_;
    requested_tiles_ = std::move(needed);
    requested_active_ = active;
    requested_position_ = p;
    if (changed) pending_ = true;
  }
  if (!changed) return;
  if (cfg_.async) {
    cv_.notify_one();
  } else {
    processPending();
  }
}

14. ロードスレッド（processPending()）

ロードスレッドの本体 workerLoop() は、cv_ で pending_（または終了の stop_）を待ち、立っていれば processPending() を呼ぶ、を繰り返すだけである。

map_tile_manager.cpp L166–175 MapTileManager::workerLoop()
void MapTileManager::workerLoop() {
  std::unique_lock<std::mutex> lk(mtx_);
  while (true) {
    cv_.wait(lk, [this] { return stop_ || pending_; });
    if (stop_) break;
    lk.unlock();
    processPending();
    lk.lock();
  }
}

processPending() は次の順に動く。ディスクの読み込みと領域の作成は、ロックを持たずに行うのが要点である。

  1. 要求を取り出す（mtx_）: requested_tiles_・requested_active_・requested_position_ をローカルにコピーし、pending_ = false、busy_ = true。
  2. 足りないタイルを読む（ロックなし）: needed のうち cache_ に無いものを、loader_->load(meta) で 1 枚ずつ順に読む。読めなければログに出して数え、そのタイルはキャッシュに入らない（次に要求が変わったときに、もう一度読もうとする）。
  3. 捨てる（ロックなし）: needed に無く、かつ現在位置から unload_radius より遠いタイルを cache_ から消す。needed に無くても 90 m 以内なら残る（第 1 部の「持ち続ける」）。
  4. 作り直すか決める: キャッシュにあるアクティブグループのタイルの組 tset を作り、アクティブグループか tset が前回（target_group_ / target_tiles_）と違えば作り直す。アクティブグループのタイルを捨てただけでも組は変わるので、作り直しになる（ほかのグループのタイルの出入りでは作り直さない）。
  5. 領域を作る（ロックなし）: tset の TileData を集めて builder_(グループ ID, アンカー, タイル) を呼ぶ。点数が min_target_points 未満なら警告を出して nullptr にする。アクティブグループが無いとき、そのグループの読み込み済みタイルが 1 枚も無いとき（ビルダーは呼ばない）、ビルダーが nullptr を返したときも nullptr。ビルダーの例外は捕まえないので、ビルダーは例外を投げないように書く（非同期モードでは、ロードスレッドから例外が出るとプロセスが終わる）。
  6. 差し替える（mtx_）: 作り直したときだけ front_ = target。統計（Stats）もここで更新する。
  7. コールバック（ロックなし）: 作り直したときだけ、setRegionCallback() で登録した関数を新しい領域（nullptr のこともある）で呼ぶ。
  8. 終わり: busy_ = false にして idle_cv_ で知らせる（waitIdle() はここで戻る）。

void MapTileManager::processPending() {
  std::set<std::size_t> needed;
  int active = -1;
  Vec2 pos = Vec2::Zero();
  {
    std::lock_guard<std::mutex> lk(mtx_);
    if (!pending_) return;
    needed = requested_tiles_;
    active = requested_active_;
    pos = requested_position_;
    pending_ = false;
    busy_ = true;
  }

  std::size_t loads = 0, failures = 0;
  for (const std::size_t i : needed) {
    if (cache_.count(i)) continue;
    try {
      cache_[i] = loader_->load(tiles_[i].meta);
      ++loads;
    } catch (const std::exception& e) {
      ++failures;
      logger_->error(std::string("failed to load tile ") + tiles_[i].meta.id.str() + ": " + e.what());
    }
  }
  for (auto it = cache_.begin(); it != cache_.end();) {
    if (!needed.count(it->first) && distanceToTile(tiles_[it->first], pos) > cfg_.unload_radius) {
      it = cache_.erase(it);
    } else {
      ++it;
    }
  }

  std::set<std::size_t> tset;
  if (active >= 0)
    for (const auto& [i, data] : cache_)
      if (static_cast<int>(tiles_[i].group_index) == active) tset.insert(i);
  const bool rebuild = active != target_group_ || tset != target_tiles_;
  std::shared_ptr<const MapRegion> target;
  if (rebuild && active >= 0 && !tset.empty()) {
    std::vector<std::shared_ptr<const TileData>> data;
    for (const std::size_t i : tset) data.push_back(cache_.at(i));
    const MapGroup& g = groups_[static_cast<std::size_t>(active)];
    target = builder_(g.id, g.anchor, data);
    if (target && static_cast<int>(target->num_points) < cfg_.min_target_points) {
      std::ostringstream os;
      os << "map group " << g.id << ": only " << target->num_points << " points around here (min_target_points "
         << cfg_.min_target_points << "), no region";
      logger_->warn(os.str());
      target.reset();
    }
  }
  if (rebuild) {
    target_group_ = active;
    target_tiles_ = tset;
  }

  RegionCallback cb;
  {
    std::lock_guard<std::mutex> lk(mtx_);
    if (rebuild) {
      front_ = target;
      cb = on_region_;
      ++stats_.target_builds;
      stats_.target_tiles = target ? target->tiles.size() : 0;
      stats_.target_points = target ? target->num_points : 0;
    }
    stats_.loaded_tiles = cache_.size();
    stats_.loaded_tiles_per_group.clear();
    for (const auto& [i, data] : cache_) ++stats_.loaded_tiles_per_group[groups_[tiles_[i].group_index].id];
    stats_.tile_loads += loads;
    stats_.tile_load_failures += failures;
  }
  if (cb) cb(target);  // waitIdle() がこの呼び出しの後に戻るよう、busy_ はここで下ろす
  {
    std::lock_guard<std::mutex> lk(mtx_);
    busy_ = false;
  }
  idle_cv_.notify_all();
}
processPending() が走るのは、update() で要る組かアクティブグループが変わったときだけである。読めなかったタイルの読み直し、遠くなったタイルの削除、領域の作り直しも、次に組が変わるまで起きない（止まっている間は何もしない）。なお requested_position_（捨てる判定の基準）は、組が変わらなくても見直しのたびに書き換わる。

activeGroup() と stats().active_group は、update() が決めた時点で新しいグループになるが、currentRegion() は作り直しが終わるまで古いグループの領域のままである。どのグループの点で照合したかは、領域の group と anchor を見る（gll_core の照合は領域の anchor で UTM に直す。一方、診断に出す active_map_group は activeGroup() なので、切り替えの直後は照合に使っている領域より先に変わる）。

currentRegion() が nullptr を返すのは、最初の処理が終わる前、アクティブグループが無いとき、アクティブグループの読み込み済みタイルが無いとき、点が min_target_points 未満のとき、ビルダーが nullptr を返したとき。

要求は上書きされ、最新の 1 つだけが処理される

要求は 1 組の変数（requested_*）で、キューではない。ロードスレッドが読み込み中に update() が何度か要求を書くと、前の要求は上書きされ、読み込みが終わった時点の最新の要求だけが処理される。古い位置のためのタイルを順に読む無駄が出ない。

アクティブグループの決め方

update() の手順 6 で、次のように決める（active_ は前回の結果）。

  • 今のアクティブグループが、まだ現在位置から load_radius 以内にある: best が別のグループで、dg[best] < dg[active] − group_switch_margin のときだけ best に切り替える。

切り替わると requested_active_ が変わるので changed になり、ロードスレッドが新しいグループのタイルで領域を作り直す。新しいグループのタイルは先読みで既にキャッシュにあることが多く、その場合は読み込みなしで領域だけ作り直す。

タイル 1 枚の読み込み（平均 約 4,900 点、共分散あり）中央値 0.28 ms
1 回の見直しで読んだタイルの数中央値 1 枚、最大 25 枚（走り始め）

作り直しの回数が読み込みの回数より多いのは、タイルを捨てただけで組が変わった回を含むからである。GICP のターゲット（KdTree の構築）の時間は、この表に含まない（既定の TileSetRegion で測った）。

メモリ

RAM に載るのは、読み込み中のタイルの分だけである。地図全体について持つのは、各タイルの範囲と点数の索引（数百 KB）だけで、点群本体は持たない。したがって、メモリは地図の広さではなく、読み込む半径の中にある点の数で決まる。

持つもの範囲西新宿（936 タイル）で走ったとき
タイルの索引（tiles_）全タイル数百 KB（tile_index.yaml は約 150 KB）
タイルのキャッシュ（点と共分散。1 点 36 バイト）読み込み中のタイル25〜58 枚（中央値 47）、最大 約 41 万点 ≒ 15 MB
GICP のターゲット（点をまとめ直したものと KdTree。1 点 約 170 バイト）同じタイル最大 約 70 MB

自己位置推定（gll_core）では、キャッシュと GICP のターゲットの両方に同じ点が入る（GICP の検索構造はタイル単位で点を消せないので、組が変わるたびにまとめ直す）。領域を作り直している間は古い領域も残るので、一時的に最大 2 倍になる。数字は点数とデータ形式からの見積もりで、実際のプロセスのメモリは測っていない。
